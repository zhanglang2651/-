# 云游 · 文旅智能助手

面向游客的 **AI 行程规划 + 城市旅游热点实时推送** 系统。基于 LangChain / LangGraph 构建智能体，接入真实气象数据与本地景点知识库，输出可直接执行的行程单与实时热度榜。

---

## 一、它能做什么

| 能力 | 说明 |
|---|---|
| **AI 行程规划** | 一句话说清目的地、天数、同行人、预算、偏好，Agent 自动查天气、挑景点、算预算、排路线，输出按天分时段的行程卡 |
| **实时热点推送** | 五因子热度模型实时计算各景点热度，SSE 每 20 秒推一次增量，带涨跌幅、拥挤度、错峰建议 |
| **AI 实时播报** | 轻量模型根据当前天气与热度榜写一段口语化播报，缓存 30 分钟 |
| **自由问答** | ReAct Agent，可自主调用天气 / 景点 / 热度 / 预算 / 精确查询五类工具 |
| **城市探索** | 30 座城市、240 个真实景点的知识库，含票价、游玩时长、最佳时段、室内外属性；点击景点可预览实景照片 |
| **城际交通查询** | 对话里问「明天贵阳到重庆的车票」，按两城直线距离推算可选方式、时长、票价区间，并给 12306 / OTA 直达链接 |
| **住宿区域建议** | 对话里问「附近推荐的酒店」，按景点库真实分布推荐住哪个区域、理由与价位区间，附 OTA 查房价入口 |
| **时令节气** | 太阳视黄经实时推算二十四节气（对照紫金山天文台误差 ≤1 天），配七十二候物候、当季出行建议与本月节庆 |
| **应季推荐** | 按城市最佳旅行季筛出"此刻正当季"的目的地，标注当月是否有节庆 |
| **玩法主题** | 8 种玩法（山水/古镇/美食/亲子/人文/夜游/漫步/避暑）聚合各城景点，带区分度门槛，点一下直接按该玩法排行程 |
| **一城一味** | 每城的地方风味清单与老饕聚集地，风味取自城市库真实字段 |
| **经典线路** | 8 条已验证的多日路线，含每日落脚点、人均预算、节奏与避坑提示，标注当前是否当季 |
| **最佳月份矩阵** | 城市 × 12 月热力图，一眼看出每座城什么时候值得去 |
| **账号体系** | 163 邮箱验证码注册登录，注册时绑定所在城市（支持浏览器定位自动识别），行程云端留存 |
| **城市影像** | 每城 3 张 Unsplash 真实照片自动轮播（4.2 秒切换），未配 key 时降级为山景剪影 |
| **单日重排** | 对已生成的行程点「改这一天」，只重排当天，其他天不动，20-40 秒 |
| **分享与导出** | 一键生成只读短链 `/s/{token}`（对方无需登录），或导出 760px 竖版长图 |
| **订单管理** | 车票 / 门票 / 酒店三类订单统一管理，支持状态流转与本月支出统计；可从行程一键生成订单草稿，并一键跳转 OTA 完成购买 |

### 权限策略

游客可浏览首页、实时热点、城市探索；**生成行程需要登录**（控制大模型成本），收藏与"我的行程"同样需要登录。

## 二、技术架构

```
┌─────────────┐
│  用户输入    │  自然语言："贵阳玩三天，带爸妈，想吃酸汤鱼"
└──────┬──────┘
       ▼
┌──────────────────────────────────────────────────────────┐
│                  LangGraph StateGraph                     │
│                                                           │
│  intake ──▶ context ──▶ compose ──▶ review                │
│  需求解析    工具调用     行程生成     结构校验             │
│              │                        │                   │
│              ├─ tool_weather          └─ 不合格 → 自动修复 │
│              ├─ tool_attractions                          │
│              └─ tool_budget                               │
└──────┬───────────────────────────────────────────────────┘
       ▼
┌────────────────┐   ┌────────────────┐   ┌──────────────┐
│  行程卡片渲染   │   │   热度引擎      │   │  ReAct Agent │
│  时间轴/预算环  │   │  20s SSE 推送   │   │  自由问答     │
└────────────────┘   └────────────────┘   └──────────────┘
```

### 热度模型（五因子加权）

```
heat = 基线热度 × 40%      ← 景点固有吸引力（人工标注 0-100）
     + 天气适配 × 20%      ← Open-Meteo 实况降水/温度 × 景点室内外属性
     + 季节契合 × 18%      ← 城市最佳旅行季区间
     + 节令势能 × 12%      ← 法定节假日 / 周末 / 工作日
     + 时段动能 × 10%      ← 景点最佳时段与当前小时的契合 + 分钟级波动
```

雨天会自动把室内景点（博物馆、溶洞）顶上来，晴天则相反——这是模型里真实发生的行为，不是随机数。

### 质量保障

- **景点白名单**：行程里的景点必须存在于候选池，编造的景点会被校验拦下并触发自动修复
- **预算自洽**：`total` 强制等于分项之和，模型算错时以分项为准
- **重复检测**：候选池够用时，同一景点不允许重复安排
- **降级兜底**：模型不可用时切换到规则模板，保证永远有可交付行程；上游天气不可用时返回明确标注的「气候估算」

## 三、快速开始

### 1. 环境要求
Python 3.10+（已在 3.13 验证）

### 2. 安装依赖

```bash
python -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt -i https://mirrors.aliyun.com/pypi/simple/
```

> 清华镜像在部分网络环境下会返回 `No versions found`，用阿里云镜像更稳。

### 3. 配置

编辑 `.env`：

```ini
# --- AI 模型 ---
SILICONFLOW_API_KEY=sk-xxxx          # 硅基流动 API Key
SILICONFLOW_BASE_URL=https://api.siliconflow.cn/v1
LLM_MODEL=Qwen/Qwen2.5-72B-Instruct  # 主力：行程规划
LLM_MODEL_FAST=Qwen/Qwen2.5-7B-Instruct  # 轻量：播报/抽取

APP_HOST=127.0.0.1
APP_PORT=8000

# --- 账号体系（163 邮箱）---
ALLOWED_EMAIL_DOMAIN=163.com
SESSION_DAYS=30
SMTP_HOST=smtp.163.com
SMTP_PORT=465
SMTP_USER=            # 你的 163 完整邮箱
SMTP_AUTH_CODE=       # 163 授权码（不是登录密码！设置→POP3/SMTP/IMAP→开启→获取）

# --- 城市真实影像（Unsplash）---
UNSPLASH_ACCESS_KEY=  # https://unsplash.com/developers 免费申请 Access Key
```

> **两处留空也能跑**：没配 SMTP 时验证码走「开发模式」，直接回填到注册表单并提示；没配 Unsplash 时城市卡自动降级为山峦剪影 + 渐变占位。

### 拉取城市照片

填好 `UNSPLASH_ACCESS_KEY` 后执行一次：

```bash
.venv\Scripts\python.exe scripts\fetch_photos.py          # 补齐缺失
.venv\Scripts\python.exe scripts\fetch_photos.py --force  # 全部重拉
```

每城 3 张横图，落在 `web/assets/photos/<city>/`，之后不再请求上游。

### 4. 启动

```bash
# 方式一
start.bat

# 方式二
.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

打开 <http://127.0.0.1:8000>

### 5. 自检

```bash
.venv\Scripts\python.exe scripts\selftest.py 8000
```

结果写入 `_selftest.txt`。

## 六、数据来源与边界

### 三类数据的诚实边界

本系统有一条明确红线：**能推算的标明是推算，能引导的给官方入口，绝不编造具体库存当真实数据卖。**

| 能力 | 怎么做 | 不做什么 | 为什么 |
|---|---|---|---|
| 城市交通 | 按两城真实经纬度算直线距离，×1.22 换算铁路营业里程，推算车型/时长/票价区间 | **不编造车次号**（如 G1234），不做实时余票 | 12306 无开放下单 API，非官方协议有法律风险且频繁封号 |
| 住宿 | 按景点库真实类型分布推荐住宿区域与价位区间 | **不编造酒店名与精确房价** | 未接入酒店集团或 OTA 库存接口 |
| 景点热度 | 五因子加权计算 | 不冒充商业平台真实客流 | 已全部标注计算方式 |
| 城市影像 | Unsplash 实拍 | 不假装是官方实景 | 已标注「与实景可能存在差异」 |

对外的每一处都附了官方/OTA 跳转按钮——系统负责「算清楚、说清楚」，最终交易交给持牌平台。

### 景点级实景照片

Unsplash 对中文景点名几乎搜不到东西（甲秀楼搜 0 条），所以景点检索词由 **LLM 离线生成**英文名后存进 `app/data/poi_queries.json`：

- 233 个景点各有 1-2 条英文检索词，生成后跑清洗脚本剔除中英混杂与过泛的兜底词
- 图片按需拉取并落地到 `web/assets/poi_photos/`，命中缓存不再打上游
- **Unsplash 免费档每小时仅 50 次搜索请求**，触发限流时接口返回 `rate_limited` 与预计恢复分钟数，前端如实告知用户而不是白屏

| 数据 | 来源 | 性质 |
|---|---|---|
| 天气实况与 7 日预报 | Open-Meteo | **真实数据**，免密钥 |
| 城市 / 景点信息 | 人工整理的知识库 | 真实景点，票价与时长用于估算 |
| 热度指数 | 五因子模型计算 | **模型推演**，非商业平台真实客流 |
| 二十四节气 | 太阳视黄经推算 | **真实天文**，与紫金山天文台一致 |
| 城际交通 | 直线距离推算 | **参考区间**，非实时余票，附 12306 链接 |
| 住宿区域 | 景点分布推算 | **参考区间**，非实时房价，附 OTA 链接 |
| 城市 / 景点影像 | Unsplash | 真实摄影作品，非官方实景 |
| 节假日 | 节令日历表 | 参考值，实际以国务院公布为准 |
| 行程文案 | LLM 生成 | 已通过结构校验，但建议出行前二次确认开放时间 |

**明确不做的事**：不伪造"实时客流"数据；不编造不存在的景点；不编造车次号与酒店报价；天气上游不可用时会显示「气候估算」而不是假装真实。

## 七、可扩展方向

1. **接真实客流**：替换 `trends.compute()` 的数据源，接入景区预约余量、地图热力图 API
2. **加向量检索**：景点库上 `pgvector` / FAISS，支持长尾城市与语义检索
3. **多人协同**：LangGraph Checkpointer 落 Redis，支持行程多版本与回滚
4. **真实地图**：接入高德/腾讯地图 SDK，把 `transport` 字段换成真实路径规划
5. **多副本部署**：限流与缓存换 Redis，`/api/plan` 的后台任务改消息队列

## 八、订单真实接入（下一步）

当前订单是**记录层**。要变成真能下单，需要一条渠道接入线：

- **A 线（跳转型）**：已实现 — 订单卡「去购买」按类型深链到携程/同程，0 资质当天可上
- **B 线（分销联盟 API）**：推荐主线 — 需企业主体，可拿佣金与真实出票状态
- **C 线（自建交易）**：不建议 — 二清合规风险

完整渠道盘点、排期与代码结构见 **[docs/订单接入方案.md](docs/订单接入方案.md)**。

`orders` 表已预留 `channel / external_order_id / pay_url / commission` 四个外部门段，接入时不需要改表结构。

## 九、登录页设计说明（暮色山河）

> 定位：文旅项目要的是「有质感的旅行感」，不是终端/机房风。整套视觉用**暖金 + 湖青 + 衬线字**，配山水与浮尘。

| 维度 | 实现 |
|---|---|
| 配色 | 暖金 `#e0a86a` × 湖青 `#6fc0b3` × 胭脂 `#d07a86`，底色 `#0a0b10` |
| 字体 | 标题与数字用衬线栈（Songti SC / STSong / Noto Serif SC / Georgia），正文用系统无衬线 |
| 氛围 | 三层暖色径向光晕 + 远山 SVG 剪影（双层）+ 6 粒缓慢上浮的浮尘 |
| 影像 | 真实城市照片做 Ken Burns 缓动轮播，叠一层 `soft-light` 暖金柔光；文字区单独加暗化层保证可读性 |
| 卡片 | 暖调玻璃拟态 + 烫金细边 + 顶部一道渐变高光 + 四角金色直角标记 |
| 页签 | 下划线式（衬线体 + 金色渐变指示线），不再用药丸按钮 |
| 输入框 | 聚焦时金色描边 + 三层柔光 + 金色 caret |
| 按钮 | 深底金字 → hover 填金并有一道斜向高光扫过；主按钮箭头位移 |
| 加载态 | 文案切「认证中 / 创建中」+ 箭头旋转，禁重复提交 |
| 交互 | 密码显隐、记住我、忘记密码、第三方入口（明确提示未开放） |
| 文案 | 「走过的路，都算数」等旅行语境的标题，字段名回归中文（邮箱/密码/验证码） |

**不依赖任何外部字体或图标库**，全部用 CSS、系统衬线字体与内联 SVG 实现。

## 十、首页设计说明（时令旅行体系）

首页原本只有"数据"（热度、地图），没有"旅行感"。这一轮按**设计节奏**补入六个模块，让用户在 30 秒内被说服"这里懂旅行"。

### 模块编排

| 位置 | 模块 | 设计意图 |
|---|---|---|
| 紧贴 Hero | **节气时令条** | 一进站就看到"今天霜降，红叶正盛"——把抽象的时间变成出行理由 |
| 第 2 屏 | **此刻正当季** | 按最佳旅行季筛选，替代泛泛的城市列表 |
| 第 3 屏 | **按心情挑玩法** | 8 种玩法卡，点一下直接带着主题去排行程 |
| 第 4 屏 | **一城一味** | 风味标签制造味觉联想，是最容易被记住的一屏 |
| 第 5 屏 | **经典线路** | 给"不想自己规划"的人一个可一键采纳的成品 |
| 第 6 屏 | **最佳月份矩阵** | 30 城 × 12 月热力图，工具属性，收藏级信息 |

### 二十四节气是算出来的，不是查表

`app/services/seasonal.py` 用**太阳视黄经**推算节气：

```
黄经 285° + 15°×n → 小寒、大寒、立春 … 冬至
二分法定位黄经过零时刻 → 转北京时间 → 定日期
```

- 精度：2026 年 24 个节气与**紫金山天文台**公布值**全部一致**（冬至算得 12-22 04:49，官方 04:50，差 1 分钟）
- 任意年份通用，不存在"表过期"
- 每个节气配**七十二候物候**（霜降 → 豺乃祭兽，草木黄落）、气候特征与出行建议

### 玩法主题要有区分度

第一版按关键词匹配，结果"山水自然"命中 30 城、"美食寻味"命中 30 城——等于没分类。改为**加权打分 + 差异化门槛**：

```
类型命中 2 分 + 标签命中 1 分 + 城市标签加分
主题门槛：美食 5 / 人文 6 / 自然 4 / 城市漫步 4 / 其余 3
```

最终分布：山水 22 城 / 人文 13 城 / 美食 14 城 / 夜游 11 城 / 古城 8 城 / 亲子 6 城 / 避暑 6 城 / 漫步 5 城。
测试用例 `test_no_theme_matches_all_cities` 守住这条下限。

### 视觉处理

- **节气条**：进度环（全年已过比例）+ 24 节气全展开（当前高亮、下一个用琥珀色标记）+ 双色光晕
- **玩法墙**：每张卡用主题自己的色相，hover 时才浮现光晕；低饱和底色避免彩虹感
- **月份矩阵**：统一青蓝色阶表示覆盖广度（不是 30 种城市色），当前月用金色描边框住；sticky 表头
- **线路卡**：真实照片做封面（Unsplash），顶部按主题色描边，叠加当季角标

### 交互闭环

节气条、应季卡、玩法卡、线路卡**不是死信息**，全部能推进主流程：

| 点击 | 行为 |
|---|---|
| 应季城市卡 / 风味卡 / 矩阵色块 | 跳城市探索并打开该城抽屉 |
| 玩法主题卡 | 填入"XX + 主题 + 2天"并触发行程规划 |
| 经典线路卡 | 填入"按「线路名」安排行程"并触发行程规划 |

未登录时会先弹登录（生成行程需要登录），与既有权限策略一致。
