# 订单真实接入方案（车票 / 门票 / 酒店）

> 目标：把「我的订单」从**记账工具**升级为**能真的买到票**。
> 前提：当前订单数据全部由用户手工录入或从行程导入，属于「记录层」。本方案解决「交易层」。

---

## 一、先划边界

| 我们做 | 我们不做 |
|---|---|
| 选品、比价、行程与订单打通 | 不碰资金归集（避免二清） |
| 下单跳转 / 回调同步状态 | 不自建支付牌照体系 |
| 佣金预估与对账记录 | 不承诺票务真实性（由渠道担保） |

**核心原则：我们做「决策 + 编排 + 履约跟踪」，交易与出票交给持牌渠道。** 这样既合规，也不用自己背库存和退改的锅。

---

## 二、渠道盘点

| 品类 | 候选渠道 | 接入方式 | 门槛 | 备注 |
|---|---|---|---|---|
| 🚄 火车票 | 12306 官方 | **无开放下单 API** | — | 非官方协议有法律风险且频繁封号，不要碰 |
| 🚄 火车票 | 携程/同程/智行 等 OTA | 分销联盟 API | 需主体资质 | 实际上车次与库存由铁路系统供给 |
| 🎫 景区门票 | 各景区官方小程序 | 无开放接口 | 需逐个对接 | 不现实 |
| 🎫 景区门票 | 携程/同程/美团/去哪儿 | 分销联盟 API | 需主体资质 | 覆盖主流景区，性价价比最高 |
| 🏨 酒店 | 携程 EBK / 飞猪 / 美团 | 分销联盟 API | 需主体资质 | 同程价格常更优，可做比价 |
| 🏨 酒店 | 品牌直连（华住、亚朵…） | 商务合作 | 需签约 | 量级起来后再谈 |

**结论：票和酒店都从 OTA 分销联盟走，火车票也走 OTA（本质是代购铁路票），不碰 12306 私有协议。**

---

## 三、三条接入线

### A 线 · 跳转型（最快，几乎零门槛）

我们不创建订单，只生成一个带参数的跳转链接，用户点一下跳到 OTA 的 H5 完成支付。

- **工作量**：0.5–1 天
- **需要**：一个 `order_channel` 表 + 链接生成器
- **优点**：不碰交易，合规风险最低，不需要任何资质
- **缺点**：用户要跳出去，体验割裂；我们拿不到佣金，转化率低
- **适合**：MVP 阶段、演示、内部先用

### B 线 · 分销联盟 API（推荐主线）

申请成为 OTA 的分销商，拿到商品库 + 下单 + 查询 + 退改四类接口。

- **典型流程**：
  1. 注册成为分销商（需要**企业主体**：营业执照、对公账户）
  2. 拿到 `product_id`（景区票种 / 酒店房型）与报价接口
  3. 我们的订单 → 调用下单接口 → 拿到 OTA 订单号 + 支付链接
  4. 用户在 OTA 页面支付
  5. 我们接收**异步回调**更新订单状态（已支付 / 已出票 / 已取消 / 已退款）
  6. 佣金按月结算，落在 `orders.commission` 字段
- **工作量**：2–3 周（含资质申请等待则更久）
- **优点**：能拿佣金、能知道真实出票状态、能做比价
- **缺点**：需要企业主体；每家 OTA 接口风格不同，要抽象一层

### C 线 · 自建交易（不建议）

自己做支付、自己出票、自己承担退改。

- **硬伤**：需要支付牌照或构成「二清」（资金先收进我们账户再结算给供应商），合规风险极高
- **票务真实性**：无法保证，容易变成「有订单无票」
- **结论**：个人/小团队阶段不要碰

---

## 四、推荐路径

```
第 1 周   A 线跑通：订单里能生成 OTA 跳转链接（不需要资质，当天可上）
第 2-3 周  B 线调研 + 主体准备：申请 1 家（建议同程或携程）分销联盟
第 4-6 周  B 线开发：OrderProvider 抽象 → 选品 → 下单 → 回调 → 对账
第 7 周+  扩品类：先门票+酒店，跑通后加火车票（走 OTA 代购）
```

**渠道选择建议**：先接 **同程** 或 **携程** 二选一。理由：覆盖率高、文档相对完整、有分销联盟后台和结算系统。接入第二家时抽象层已经就位，边际成本很低。

## 五、数据模型（已预留）

`orders` 表已经加好外部门��，接入时不需要改表结构：

| 字段 | 含义 |
|---|---|
| `channel` | `manual` / `ctrip` / `tongcheng` / `meituan` / `fliggy` |
| `external_order_id` | 渠道侧订单号，用于对账与状态查询 |
| `pay_url` | 支付/跳转链接（A 线直接用，B 线下单后回填） |
| `commission` | 预估或实际佣金 |

状态机沿用现有四态：
```
pending(待支付) → paid(已支付) → used(已使用)
        ↓
   cancelled(已取消/已退款)
```
渠道回调只需把外部状态映射进这四态，前端不用改。

## 六、接入层建议代码结构

```
app/
  services/
    channels/
      __init__.py        # OrderProvider 抽象 + get_provider(channel)
      base.py            # 统一接口：search / create_order / query_status / refund
      manual.py          # 现有纯记录模式（已实现，等价于"无渠道"）
      tongcheng.py       # 渠道实现（待开发）
      ctrip.py           # 渠道实现（待开发）
  api/
    routes_channel.py    # 选品 / 报价 / 下单 / 回调
```

`OrderProvider` 抽象接口（4 个方法）：

```python
class OrderProvider:
    name: str
    async def search(self, city, kind, **kw) -> list[Product]: ...
    async def quote(self, product_id, **kw) -> Quote: ...
    async def create_order(self, product_id, user, **kw) -> ExternalOrder: ...
    async def query_status(self, external_order_id) -> str: ...
```

这样新增一家渠道只写一个文件，业务代码零改动。

## 八、现在就能做的 MVP（A 线，半天）

1. `orders` 增加 `pay_url` 字段写入（字段已加好）
2. 订单卡片加「去购买」按钮，指向对应 OTA 搜索页
3. 车站/景区/酒店按「城市 + 名称」生成深链：
   - 携程：`https://you.ctrip.com/searchsite/?keyword={关键词}`
   - 同程：`https://www.ly.com/hotel/hotelsearch?keyword={关键词}`
4. 点「去购买」前先本地落一条 `pending` 订单，回调回来时更新状态

这样订单系统当天就能从「记账」变成「能跳转下单」，等资质到位再升级为 B 线的完整闭环。
